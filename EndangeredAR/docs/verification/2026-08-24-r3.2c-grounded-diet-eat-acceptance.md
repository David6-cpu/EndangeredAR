## Scope

R3.2C permits one automatic character action only when a positive natural-diet
question is answered from canonical diet evidence. The accepted path is:

`Canonical retrieval -> trusted grounding metadata -> grounded candidate ->
ActionPolicy -> capability -> validator -> one-shot Eat -> Idle`

The model still owns only reply prose. It cannot grant a grounding topic,
fact ID, citation, Eat permission, Animator parameter, or Unity method call.
The existing action transport continues to reject Eat.

This phase does not add a new animation, action queue, interruption, emotion,
task context, reward/progress mutation, streaming, native inference, or a
second animal.

## Trusted grounding contract

Python's canonical retrieval result now owns these response fields:

- `answerMode`
- `evidenceStatus`
- `groundingTopic`
- `groundedFactIds`
- `citations`
- `approvedAnswer`

`GroundingTopic` contains only `None` and `Diet`. The wire representation is
strict: exact lowercase `diet` maps to `Diet`; missing, empty, differently
cased, padded, concatenated, unknown, or action-like strings map to `None`.
There is no trimming, case folding, substring match, or permissive enum parse.

`groundedFactIds` contains the stable, deduplicated canonical fact IDs actually
used by the answer. It remains empty for social chat, off-domain responses,
known unknowns, insufficient evidence, missing citations, and mixed-topic
evidence. Provider prose cannot overwrite these application-owned fields.
Older servers that omit them remain compatible and fail closed.

## Precise quantity guard

Both Python retrieval and the Unity canonical fallback use the shared precise
diet-quantity fixture. Requests for unsupported exact amounts, units, daily or
per-meal quantities, or fabricated numbers become insufficient evidence even
if a general diet fact would otherwise match.

For `你每天准确吃多少克叶子？`, the accepted behavior is:

- no invented number
- `insufficient_evidence`
- `GroundingTopic.None`
- no grounded action candidate
- no Eat

The guard classifies a bounded request pattern rather than one complete hard-
coded sentence.

## Unity knowledge fallback

The Unity local-knowledge result preserves canonical knowledge ID, topic, and
source IDs. Its provider adapter emits the same grounding topic, fact IDs,
citations, answer mode, and evidence status as the server path. Missing topic,
fact ID, source relation, or citation fails closed and cannot authorize Eat.

Local LLM, Cloud LLM, server knowledge, and trusted Unity knowledge therefore
share the same evidence boundary. Provider selection does not change action
permission. Server-rule responses without canonical grounding metadata cannot
authorize Eat.

## Intent and candidate boundary

`GroundedDietIntentClassifier` performs the Unity-owned second check against
the original user message. Positive natural-diet questions are eligible.
Negative or retrospective language, human snacks and unsafe-feeding questions,
unsupported precise quantities, technical Animator/action language, prompt
injection, and business-state commands are rejected before candidate creation.

`GroundedActionCandidateFactory` creates at most one candidate and has no
execution capability. It requires all of the following:

- grounded fact answer mode
- evidence found
- exact `GroundingTopic.Diet`
- non-empty canonical fact IDs
- every fact belongs to the current animal and has topic `diet`
- non-empty citations whose source IDs match those facts and their canonical
  source relationships
- matching response/current animal
- positive diet intent with no rejected context

The result is only `ActionCandidate(Eat, GroundedKnowledge, animalId)`. It must
still pass the existing policy, capability profile, completion validity,
one-shot validator token, current model lookup, controller support, and Busy
state before execution.

## Transport isolation and conflict policy

Action transport remains unchanged and strict:

- `eat` -> `AIAction.None`
- `Eat` -> `AIAction.None`
- `EAT` -> `AIAction.None`
- padded or concatenated Eat strings -> `AIAction.None`

Neither Local nor Cloud model metadata can request Eat. Eat is derived only
from authenticated grounding metadata and the original user question.

Whole-branch review found one pre-acceptance blocker: a real grounded HTTP
response carries transport action `None`, so a mixed Taunt/diet request could
initially expose only Eat instead of reaching the existing multi-action
conflict rule. Commit `1612ca0a` fixed this by deriving deterministic Taunt
only when a trusted grounded Eat candidate already exists, solely so the
existing ActionPolicy sees both candidates and fails closed. Provider-less or
non-grounded Taunt behavior is unchanged.

For `给我表演一下，再告诉我你吃什么。`, the final behavior is:

- reply and citations remain available
- Taunt does not execute
- Eat does not execute
- no priority is guessed

Independent re-review found no remaining blocking issue.

## Completion and history behavior

The accepted completion order is:

1. accept the current completion ticket
2. display reply
3. display citations
4. save text history once
5. restore input state
6. consume at most one validated action token
7. request Eat from the current controller

Action failure never rolls back or duplicates the answer. Busy actions are not
queued or retried. Stale, duplicate, wrong-animal, inactive-page, unsupported,
or switched-model completions cannot execute. No Animator or model reference is
cached across the completion lifecycle.

Chat history keeps its existing text/citation-compatible schema. It does not
store grounding topic, grounded fact IDs, candidate, action eligibility, or
execution result. Restoring a diet conversation never recreates or replays Eat.

## Security and release boundary

- `.env.local`, local model weights, signing material, Xcode user data, device
  identifiers, and iOS build outputs remain outside Git.
- Model text cannot create or overwrite grounding metadata.
- Citation URL/title prose is never used as execution authority; canonical
  source IDs and fact/source relationships are required.
- Development tools remain excluded from non-Development players by the
  existing compile/build isolation contract; R3.2C did not modify that path.
- Eat still cannot be requested through provider action transport.
- No task, progress, badge, reward, unlock, animation asset, Animator, prefab,
  scene, or capability profile was modified in this phase.

## Residual risk

Candidate authorization canonicalizes fact and source relationships by stable
IDs. Citation display labels received from trusted application transports are
not independently replaced from local canonical data. They are not execution
authority, and all normal application-owned paths are covered, but fully
canonicalized citation display metadata is a non-blocking hardening option for
a later phase.

The physical-device checks are human-observed functional acceptance, not an
automated UI test or quantitative performance benchmark.

## Decision

R3.2C is accepted. Local, Cloud, and Unity canonical knowledge paths can produce
one Eat candidate only from verified diet evidence and a positive diet question.
Transport Eat remains rejected; unsafe, unsupported, mixed, stale, busy, and
historical paths fail closed without losing the answer or citation.

This report does not authorize merge, push, R3.3, additional actions, emotion,
task context, action queues, streaming, native inference, or UI redesign.
