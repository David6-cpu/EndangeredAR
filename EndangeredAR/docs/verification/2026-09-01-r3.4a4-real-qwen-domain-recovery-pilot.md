# R3.4A.4 Real-Qwen Response Domain Recovery Pilot

Date: 2026-09-01

Branch under test: `codex/r3.4a4-real-qwen-domain-recovery`

## Decision

**Do not continue to full Qwen-domain learned-model retraining. R3.4A remains
not fully accepted, and R3.4B remains closed.**

The frozen TextCNN Pair candidate reproduced the response-domain failure and
accepted only 5 of 30 Pilot Greeting pairs. None of the frozen learned
strategies improved on the deterministic rule while retaining zero
safety-critical false positives. Rule-only produced the best Pilot tradeoff:
precision `1.0000`, recall `0.8667`, and 0 safety-critical false positives.

The Pilot therefore recommends ending the learned-classifier requirement for
the first Greeting-to-Wave path. A future product proposal should evaluate the
deterministic Greeting Intent together with Product Scope and the existing
application-owned action gates. This report does not approve Wave, modify the
action system, or constitute that separate deterministic-gate acceptance.

## Development safe-pair capture

The Development-only capture path now reads the accepted completion snapshot
instead of matching an exact assistant string. It records only the latest
in-memory final validated pair and its strong-type metadata after all of these
checks pass:

- approved fixed research prompt ID;
- final source is `on_device_llm`;
- language generator is `OnDeviceLlm`;
- response validation passed;
- completion ID is current rather than stale;
- response is not `system_status`;
- pair is captured only through the explicit
  `CAPTURE CURRENT SAFE PAIR` button.

Automated coverage proves that the science prompt can be captured with a
variable validated reply, and that stale, validation-failed, system-status,
and unapproved pairs fail closed. The snapshot is not automatically persisted
and does not read native prompts, Memory JSON, Progress, or chat history.

This Pilot did not repeat the signed-device capture UI pass. The capture
contract passed 5 focused EditMode tests and the complete EditMode suite.

## Error analysis

The frozen Pair and Reply-only TextCNNs learned the authored assistant style
used in the earlier recovery corpus. Production-semantics Qwen replies vary in
length, phrasing, persona framing, and whether the reply restates the greeting.
Those changes can dominate the Pair representation even when the user's intent
is unambiguously a greeting.

User-only models avoid assistant variation, but the frozen learned-only models
accepted quoted, technical, or product negatives. Reapplying the deterministic
rule removed those false positives and then provided no recall gain over
Rule-only. The simple reply compatibility guard also reduced recall without
improving precision.

A separate tokenizer boundary defect surfaced during the Pilot: a 94-character
reply could create 97 tokens despite the locked maximum length of 96. The
encoder now clamps the reply segment to the remaining 93 positions, with a
regression test. Vocabulary, checkpoint, thresholds, temperature, and model
weights were not changed.

## Exit recommendation

Generating 2,200 more Qwen-domain pairs and retraining is not justified by
this Pilot. The learned gate did not demonstrate product value beyond the
deterministic rule, while Pair and Reply-only models introduced substantial
response-style sensitivity.

Recommended next decision, in a separately authorized stage:

`DeterministicGreetingIntent + ProductScopeGate + existing application-owned
action safety gates`

The affect classifier remains research-only. No new checkpoint or ONNX was
exported, and no Unity or iPhone model gate was rerun because no learned
candidate was selected. No Gold v3 was created or reviewed.
