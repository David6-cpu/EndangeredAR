# R3.3B Event-based Character Memory Acceptance

Date: 2026-08-25

Branch: `codex/r3.3b-event-memory`

Baseline: `453f95757ce3c980e858ff111d00ea07b62ef844`

Status: accepted. Device evidence, local whole-branch review, focused defect
verification, and final full regression are complete.

## Scope

R3.3B adds a separate, versioned, bounded event-memory store for real business
milestones:

`saved Progress transition`
`-> strong typed Memory event batch`
`-> character-memory.json`
`-> deterministic read-only projection`

Progress remains the only source of truth. Memory does not write Progress,
Mission, Catalog, Badge, chat history, grounding metadata, action candidates,
capabilities, or Animator state.

The Memory projection is deliberately not injected into `AIRequest`, prompts,
Local or Cloud providers, or the R3.3A read-only context. R3.3C has not started.
There is no LLM summarizer, free-text relationship memory, affection value,
nickname, account, cloud sync, or AI-owned Memory write path.

## Schema and privacy

`CharacterMemoryDocument` is stored independently from
`animal-progress.json`. The schema contains:

- document `schemaVersion`
- local partition `profileKey` (`local-default`)
- animal-scoped records
- bounded live events
- deterministic folded milestone counts
- bootstrap/reconciliation and clear-suppression metadata

Each supported event contains a schema version, event ID, stable idempotency
key, profile key, animal ID, strong event type, controlled subject ID, UTC
timestamp, and origin. IDs are validated and bounded before persistence.

The store never contains a real name, email, location, device ID, Apple ID,
API credential, local path, prompt, user message, LLM reply, or complete chat
history. `profileKey` is only a local partition and is not a user account or a
device-derived identifier. The Memory file is local application data and is
not tracked by Git or sent to a model.

## Supported events

R3.3B supports four authority-backed milestones:

- `AnimalDiscovered`
- `MissionCompleted`
- `KnowledgeLearned`
- `BadgeEarned`

`KnowledgeViewed` and `GroundedTopicDiscussed` are intentionally excluded.
Chat replies, history restoration, Taunt, Eat, AI completions, and page views
do not produce Memory events.

Stable idempotency keys use this shape:

`v1|profileKey|animalId|eventType|subjectId`

The event ID and idempotency key have separate responsibilities. Repeating the
same successful business operation does not add another event. Different
profiles and animals remain isolated.

## Save ordering and failure behavior

`AnimalProgressService` uses copy-on-write for progress mutation. A successful
operation follows this order:

1. build the proposed Progress copy and transition batch;
2. persist Progress;
3. replace the in-memory Progress snapshot;
4. send the successful transitions to the Memory sink;
5. notify `ProgressChanged`.

If Progress persistence fails, neither the in-memory snapshot nor Memory is
changed. If Memory persistence fails after Progress succeeds, Progress is not
rolled back. The product continues, emits only a sanitized diagnostic, and a
later deterministic reconciliation can restore missing supported milestones.

Mission completion now carries a stable canonical `missionId` into the
transition instead of relying on UI text. Repeated mission, knowledge, badge,
and discovery calls remain idempotent.

## Repository reliability

`JsonCharacterMemoryRepository` uses a dedicated file, temporary-file write,
flush, atomic replacement, and backup recovery. Missing files load as an empty
document. A damaged primary can recover from its backup without changing
Progress. Unknown JSON fields remain compatible. An unsupported future schema
version fails closed and is not overwritten by the current build.

Repository errors do not crash chat or business flows and are not shown as
technical errors to ordinary users.

## Capacity and projection

Each profile and animal keeps at most 64 live structured events. When the cap
is reached, the oldest supported event is deterministically folded into typed
milestone counts before a new event is stored. Unknown future event types are
never folded into a current projection.

`CharacterMemoryProjection` is deterministic and contains:

- discovery state/count
- completed mission IDs
- learned knowledge IDs
- earned badge IDs
- at most eight recent typed milestones

Set-like outputs are deduplicated and stably ordered. Projection does not use
an LLM and does not persist a free-text summary. Damaged or unknown events are
ignored without invalidating supported events.

## Bootstrap, reconciliation, and clear

For an existing installation without a Memory file, a one-time bootstrap
derives supported milestone events from the current Progress snapshot. These
events use bootstrap origin and do not claim to have happened at app launch.
Their stable idempotency keys prevent later business calls from duplicating
them.

Reconciliation compares Progress with Memory and only adds missing supported
milestones. Progress always wins when the two disagree; Memory can never
change Progress.

`ClearAnimalMemory` and `ClearAllCharacterMemory` clear only Memory. They do
not clear unlock state, missions, knowledge, badges, catalog state, or chat
history. Clear writes suppression metadata so reload, reconciliation, and app
restart do not immediately recreate the cleared milestones. A later real
business transition removes only its corresponding suppression and can be
recorded normally. The clear operation is therefore real rather than a visual
reset that instantly repopulates.

## Development-only inspection

The Development panel resolves the active animal and Memory service when it
refreshes. It displays only availability, live event count, and the compact
projection counters. It provides fixed clear-current, clear-all, and reload
operations and never exposes arbitrary event creation, JSON editing, AI input,
or Animator control.

The panel and bootstrap code are compiled only for Editor or Development
builds. A non-Development Player smoke build succeeded, and the Player runtime
assembly contained neither the Memory panel nor the development bootstrap
types. No `DEV` UI or Missing Script appeared at runtime.

## Physical-device acceptance

The Unity 6000.0.76f1 Development build exported, signed, installed, and
launched successfully on the physical test device. No signing identity,
profile identifier, account information, or device identifier is recorded in
this report.

Manual results:

| Check | Result |
| --- | --- |
| Existing Progress bootstrap | `sensen` store available; 4 live events; projection `D1 M1 K1 B1` |
| Repeat an already completed operation | Event count and projection unchanged |
| App termination and restart | Event count and projection unchanged |
| Clear current animal | `0 / D0 M0 K0 B0` |
| Business state after clear | Unlock, mission, knowledge, badge, and chat remained |
| Reload after clear | Still `0 / D0 M0 K0 B0` |
| App restart after clear | Still `0 / D0 M0 K0 B0`; business state unchanged |
| Grounded diet chat | Correct answer, real citation, Eat once, returned to Idle |
| Long-term-memory isolation | Reply did not claim long-term memory; Memory remained empty |
| Taunt | Played once and returned to Idle; Memory remained empty |
| Gestures and navigation | Rotation, pinch zoom, and page switching remained normal |

The device already contained completed Progress, so first-time discovery,
mission, knowledge, and badge transitions could not be honestly repeated one
by one. The device bootstrap proved the four persisted milestone types, while
fresh-transition fixtures prove the post-save live path and duplicate
suppression. Physical second-animal isolation is unavailable in the current
single-animal product, and corrupting an app-sandbox file was not exposed as a
device operation; automated PlayMode tests cover those cases. Clear-all is
also covered automatically rather than claimed as a manual device step.

No complete Memory JSON was logged or captured during acceptance.

## Isolation from R3.3A, R2, and R3 actions

R3.3A real-time context continues to read unlock, knowledge count, badge count,
and mission completion directly from Progress. Memory cannot override these
values.

R2 canonical facts, citations, evidence status, and grounded fact IDs are
unchanged. Memory does not create or modify grounding topics.

R3 actions remain authorized only through candidate, policy, capability,
validator, one-shot token, and controller. Memory does not create Taunt or Eat
candidates. Device chat and action acceptance left the cleared Memory
projection at `0 / D0 M0 K0 B0`.

## Branch review

The requested external independent Codex review was attempted with explicit
repository-only and no-credential boundaries. The environment security policy
rejected that action because it would transmit private branch code to an
external review service. The policy was not bypassed, and this report does not
claim that an independent review passed.

A local whole-branch diff review was performed instead. It covered repository
commit semantics, backup recovery, Progress save ordering, idempotency,
capacity, bootstrap/reconciliation, clear suppression, future-schema handling,
privacy, AI/action isolation, Development-only compilation, and whether the
tests exercise real file and runtime behavior.

The local review found and closed two issues:

- Unity folder metadata contained trailing whitespace, which made a true
  base-to-HEAD `git diff --check` fail.
- A backup refresh could fail after the primary Memory file was already
  committed, causing a successful disk write to be reported as failed. A RED
  file-system test reproduced the `UnauthorizedAccessException`; the repository
  now treats post-commit backup refresh as best-effort while retaining the
  previous valid backup. The focused repository suite passed 12/12 after the
  fix.

No unresolved blocking finding remained after these fixes and the final full
regression.

## Known limitations and next gate

- R3.3B records only four durable business milestones; interaction/page-view
  memories remain out of scope.
- The current product has one local profile and one completed animal flow, so
  multi-user and physical multi-animal checks remain future work.
- Bootstrap records known current state, not the historical time at which the
  original milestone occurred.
- No Memory-aware dialogue exists. R3.3C requires a separate design and
  authorization before a minimal deterministic projection may enter AI
  context.

R3.3B is ready for local merge review. It has not been merged or pushed, and
R3.3C still requires separate design and authorization.
